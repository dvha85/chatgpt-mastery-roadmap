## 0. Terms first — Giải thích thuật ngữ trước

- **output contract / hợp đồng đầu ra**: mô tả rõ output phải có hình dạng, trường thông tin và quy tắc nào để được chấp nhận.
- **format / định dạng**: cách sắp xếp đầu ra, ví dụ bảng, bullet, JSON, memo.
- **field / trường thông tin**: một thành phần cụ thể trong cấu trúc, ví dụ `Price` hoặc `Risk`.
- **schema / lược đồ**: mô tả cấu trúc dữ liệu và loại trường; ở Stage A chỉ cần hiểu khái niệm, chưa cần kỹ thuật API.
- **checklist / danh sách kiểm**: danh sách các điều bắt buộc phải có hoặc phải kiểm.
- **example / ví dụ mẫu**: một output minh họa giúp làm rõ ý định; không phải source of truth.
- **acceptance criteria / tiêu chí chấp nhận**: điều kiện để quyết định output PASS hay FAIL.

## 1. Learning objectives — Mục tiêu học tập

### English
By the end of this lesson, you can:

- specify a useful output structure before asking ChatGPT to generate it
- choose tables, bullets, checklists, or prose based on the task
- define required fields and rules without over-constraining the answer
- review a response against an explicit checklist

### Tiếng Việt
Sau bài này, bạn có thể:

- định nghĩa cấu trúc đầu ra hữu ích trước khi yêu cầu ChatGPT tạo nội dung
- chọn table, bullet, checklist hoặc prose phù hợp với task
- nêu field và rule bắt buộc mà không bó cứng output quá mức
- review response bằng checklist rõ ràng

## 2. Key vocabulary — Từ vựng trọng tâm

| Term | Nghĩa tiếng Việt | Plain English | Trong ChatGPT |
|---|---|---|---|
| `output contract` | hợp đồng đầu ra | A clear description of the expected result shape and rules. | Quy định format + required fields + acceptance rules. |
| `format` | định dạng | The way information is arranged. | Table, bullets, memo, numbered steps. |
| `field` | trường thông tin | One named piece of information. | Option, Cost, Evidence, Risk. |
| `schema` | lược đồ | A formal structure for data. | Stage A: hiểu khái niệm; kỹ thuật JSON schema học sau. |
| `checklist` | danh sách kiểm | A list used to verify required items. | Dùng để review output. |
| `example` | ví dụ mẫu | A sample that illustrates the desired result. | Giúp làm rõ tone/shape; không phải dữ kiện thật. |
| `acceptance criteria` | tiêu chí chấp nhận | Conditions for PASS. | Dùng để đánh giá trước khi tin hoặc sử dụng output. |

## 3. Core concept — Khái niệm cốt lõi

### English
If you know how the result will be used, describe that shape before generation. A useful output contract reduces ambiguity and makes verification easier. It does not need to be technical.

### Tiếng Việt
Nếu bạn biết kết quả sẽ được dùng thế nào, hãy mô tả hình dạng đầu ra trước khi sinh nội dung. Output contract tốt giảm mơ hồ và làm verification dễ hơn. Không cần phải là schema kỹ thuật.

## 4. Choose the simplest useful format — Chọn format đơn giản nhất đủ dùng

### Use prose / đoạn văn khi

- cần giải thích hoặc lập luận liên tục;
- số lượng item ít;
- quan hệ giữa ý quan trọng hơn so sánh từng cột.

### Use bullets / bullet khi

- cần scan nhanh;
- item độc lập;
- next steps hoặc findings ngắn.

### Use a table / bảng khi

- cần so sánh nhiều option theo cùng criteria;
- cần kiểm missing values;
- dữ liệu có cấu trúc lặp.

### Use a checklist / danh sách kiểm khi

- output phải thỏa nhiều điều kiện;
- cần review PASS/FAIL;
- thao tác có trình tự hoặc risk.

**Rule / Quy tắc:** chọn format vì mục đích sử dụng, không vì nhìn “chuyên nghiệp”.

## 5. Output contract anatomy — Cấu tạo hợp đồng đầu ra

Một output contract có thể gồm:

```text
Format:
Required fields:
Ordering:
Length/detail:
Unknown handling:
Acceptance criteria:
```

### Example

```text
Return a table with exactly these columns:
Option | Monthly cost | Custom domain | Setup difficulty | Main trade-off | Evidence status

Rules:
- one row per option
- use Unknown when evidence is missing
- do not invent a value to fill an empty cell
- sort by monthly cost from low to high only when all compared costs are verified

After the table, write a recommendation in no more than 120 words.
```

**Giải thích:** contract quy định structure và missing-data behavior, nhưng vẫn để model diễn giải trade-off.

## 6. Example vs rule — Ví dụ khác quy tắc

Một ví dụ có thể giúp hiểu style:

```text
Example row:
Tool A | $10/month | Yes | Easy | Fewer advanced controls | Verified
```

Nhưng ví dụ **không có nghĩa** mọi row phải có giá, feature hay pattern giống hệt. Nếu điều gì bắt buộc, hãy viết thành rule hoặc acceptance criterion.

## 7. Full example — Ví dụ trọn vẹn

### Weak request / Yêu cầu yếu

```text
Compare the plans nicely.
```

### Strong output contract / Hợp đồng đầu ra rõ

```text
Compare the three plans in a table with these columns:
Plan | Monthly price | Included storage | Support | Best for | Unknowns

Use only the provided data. If a value is missing, write Unknown.
After the table:
1. recommend one plan for a solo freelancer;
2. give two reasons;
3. state one downside;
4. keep the recommendation under 100 words.
```

### Verification checklist

- [ ] exactly six table columns
- [ ] all three plans included
- [ ] missing values labeled `Unknown`
- [ ] no new facts introduced
- [ ] recommendation has two reasons and one downside
- [ ] recommendation under 100 words

## 8. Guided practice — Bài có hướng dẫn

Input giả lập:

| Tool | Price | Custom domain | Maintenance |
|---|---:|---|---|
| A | $9 | Yes | Low |
| B | $14 | Yes | Medium |
| C | Unknown | No | Low |

Hãy viết prompt để nhận:

1. bảng có `Tool`, `Price`, `Custom domain`, `Maintenance`, `Fit`;
2. `Fit` chỉ dùng `Strong`, `Possible`, `Weak`;
3. budget là dưới $15/tháng;
4. custom domain bắt buộc;
5. không suy đoán giá C;
6. sau bảng có một recommendation tối đa 80 từ.

### Sample solution / Đáp án mẫu

```text
Using only the table I provide, return a comparison with these columns:
Tool | Price | Custom domain | Maintenance | Fit

Fit must be one of Strong, Possible, or Weak.
Assume the user needs a custom domain and a budget below $15/month.
Do not infer Tool C's missing price; keep it Unknown.
After the table, recommend one option in no more than 80 words and state one trade-off.
```

## 9. Self practice — Bài tự làm

Tạo output contract cho một trong ba task:

1. tóm tắt một cuộc họp;
2. so sánh 4 sản phẩm;
3. lập kế hoạch học 7 ngày.

Output contract phải có:

- format;
- ít nhất 4 required fields/items;
- một rule cho missing/unknown information;
- ít nhất 3 acceptance criteria;
- một giới hạn độ dài hoặc độ chi tiết hợp lý.

Sau đó chạy prompt và chấm output theo checklist.

## 10. Rubric — Cách chấm

Chấm 0–2 cho mỗi nhóm:

| Nhóm | 0 | 1 | 2 |
|---|---|---|---|
| Structure | không rõ format | có format nhưng thiếu field quan trọng | format/fields phù hợp use case |
| Rules | không có | có rule nhưng mơ hồ | rules quan sát/kiểm được |
| Unknown handling | dễ buộc model đoán | có nhắc nhưng chưa cụ thể | ghi rõ Unknown/ask/omit behavior |
| Acceptance | không có | có nhưng khó kiểm | có checklist/criteria rõ |

**PASS:** tổng ít nhất 6/8, không nhóm nào 0.

## 11. English patterns for AI work — Mẫu câu tiếng Anh dùng với AI

| Pattern | Nghĩa / cách dùng |
|---|---|
| `Return the result as a ...` | Chỉ định format. |
| `Use exactly these columns ...` | Cố định cột khi thật sự cần. |
| `Include one row for each ...` | Quy định đơn vị lặp. |
| `If the value is missing, write Unknown.` | Xử lý dữ liệu thiếu. |
| `After the table, ...` | Thêm phần narrative sau structured output. |
| `The output passes if ...` | Nêu acceptance criterion. |

## 12. Verification — Kiểm chứng

Output đúng format chưa chắc đúng fact. Hãy tách hai lớp kiểm:

### Structure check / Kiểm cấu trúc

- đúng số cột/section?
- có đủ required fields?
- có vi phạm length/order/rules?

### Content check / Kiểm nội dung

- field có dựa trên input/source không?
- missing value có bị bịa để “đủ bảng” không?
- recommendation có dùng đúng criteria không?

## 13. Failure modes — Lỗi thường gặp

- Ép table cho nội dung cần giải thích dài.
- Yêu cầu quá nhiều cột không phục vụ quyết định.
- Cho example nhưng không nêu rule, rồi kỳ vọng model hiểu example là bắt buộc.
- Ép model điền đủ mọi ô dù source thiếu dữ liệu.
- Chỉ kiểm format mà bỏ qua factual correctness.
- Dùng schema kỹ thuật khi người học mới chỉ cần bảng/checklist dễ đọc.

## 14. PASS criteria — Tiêu chí PASS

### ChatGPT track

- [ ] Explain: giải thích output contract và acceptance criteria.
- [ ] Execute: tạo một contract có format, fields, rules và checklist.
- [ ] Diagnose: tìm một contract bị over-constrained hoặc thiếu unknown handling.
- [ ] Verify: chấm response theo structure + content check.
- [ ] Transfer: áp dụng sang task khác loại.

### English track

- [ ] Recognize 6/7 thuật ngữ.
- [ ] Understand `field`, `checklist`, `acceptance criteria`.
- [ ] Use ít nhất hai output-instruction patterns bằng tiếng Anh.
